# Terraform Workflow

**Exam Objectives Covered:** 3a, 3b, 3c, 3d, 3e, 3f, 3g

## Overview

The core Terraform workflow follows four stages. Each builds on the last and serves a distinct purpose.

```
Write Config → terraform init → terraform plan → terraform apply → (terraform destroy)
```

---

## Stage 1: Write Your Configuration

Before running any commands, you write `.tf` files describing the infrastructure you want.

```hcl
# main.tf
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
}
```

Terraform doesn't do anything yet — it just reads these files when you run commands.

---

## Stage 2: terraform init

```bash
terraform init
```

**What it does:**

- Downloads the **provider plugins** specified in your configuration (e.g., AWS, Azure, GCP)
- Downloads any **modules** referenced in your config
- Initialises the **backend** (local or remote state storage)
- Creates the `.terraform/` directory where plugins and modules are cached
- Creates `.terraform.lock.hcl` to lock provider versions

**You must run `terraform init`:**
- When starting a new project
- After adding or changing a provider
- After adding or changing a module
- After changing the backend configuration

**Output example:**
```
Initializing the backend...
Initializing provider plugins...
- Finding hashicorp/aws versions matching "~> 5.0"...
- Installing hashicorp/aws v5.31.0...

Terraform has been successfully initialized!
```

> The `.terraform/` directory should be added to `.gitignore` — it's large and regenerated by `init`.

---

## Stage 3: terraform plan

```bash
terraform plan
```

**What it does:**

- Reads your `.tf` configuration files
- Reads the current state file to understand what already exists
- Calls the provider APIs to check the real state of resources (refresh)
- Computes the **diff** — what needs to be created, changed, or destroyed
- Prints an execution plan but **makes no changes**

This is your safety check before touching real infrastructure.

**Reading the plan output:**

| Symbol | Meaning |
|---|---|
| `+` | Resource will be **created** |
| `-` | Resource will be **destroyed** |
| `~` | Resource will be **updated in place** |
| `-/+` | Resource will be **destroyed and recreated** |

**Example output:**
```
Terraform will perform the following actions:

  # aws_instance.web will be created
  + resource "aws_instance" "web" {
      + ami           = "ami-0c55b159cbfafe1f0"
      + instance_type = "t2.micro"
      ...
    }

Plan: 1 to add, 0 to change, 0 to destroy.
```

**Saving a plan:**
```bash
terraform plan -out=tfplan    # save plan to a file
terraform apply tfplan        # apply exactly that saved plan
```

Saving a plan guarantees that what you reviewed is exactly what gets applied — useful in CI/CD pipelines.

---

## Stage 4: terraform apply

```bash
terraform apply
```

**What it does:**

- Runs a plan (unless you pass a saved plan file)
- Shows the execution plan and prompts for confirmation
- Provisions, modifies, or deletes resources via the provider APIs
- Updates the state file to reflect the new reality

**Confirmation prompt:**
```
Do you want to perform these actions?
  Terraform will perform the actions described above.
  Only 'yes' will be accepted to approve.

  Enter a value: yes
```

Type `yes` to proceed. Anything else cancels.

**Skip the prompt (use carefully):**
```bash
terraform apply -auto-approve
```

> `-auto-approve` is common in automated pipelines but should never be used casually — there is no undo for infrastructure changes.

**After a successful apply:**
```
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
```

The state file is updated immediately. If apply fails partway through, the state reflects only what was successfully created — partial state is normal and recoverable.

---

## Stage 5: terraform destroy

```bash
terraform destroy
```

**What it does:**

- Plans the destruction of **all resources** tracked in state
- Prompts for confirmation
- Deletes every managed resource in reverse dependency order
- Clears the state file

**Example output:**
```
Terraform will perform the following actions:

  # aws_instance.web will be destroyed
  - resource "aws_instance" "web" {
      ...
    }

Plan: 0 to add, 0 to change, 1 to destroy.

Do you really want to destroy all resources?
  Enter a value: yes
```

**Destroy a specific resource only:**
```bash
terraform destroy -target=aws_instance.web
```

**Skip the prompt:**
```bash
terraform destroy -auto-approve
```

> Destroy is permanent. Resources are deleted from the cloud provider. Use `-target` to limit scope when you only want to remove part of your infrastructure.

## Other Useful Commands in the Workflow

### terraform validate

```bash
terraform validate
```

Checks your configuration for syntax errors and internal consistency. Does not connect to any provider or check state. Run this before `plan` to catch mistakes early.

### terraform fmt

```bash
terraform fmt
```

Automatically formats your `.tf` files to the standard Terraform style. Good habit before committing code.

### terraform show

```bash
terraform show          # show current state in human-readable form
terraform show tfplan   # show a saved plan file
```

### terraform output

```bash
terraform output                  # show all outputs
terraform output instance_ip      # show a specific output value
```

---

## Full Workflow in Order

```bash
# 1. Write your .tf files

# 2. Initialise the working directory
terraform init

# 3. Check for syntax errors
terraform validate

# 4. Format code
terraform fmt

# 5. Preview what will happen
terraform plan

# 6. Apply the changes
terraform apply

# 7. When done, tear it down (labs/dev only)
terraform destroy
```

---

## What Happens to State at Each Stage

| Command | State Effect |
|---|---|
| `init` | No change to state; sets up backend |
| `plan` | Reads state; no change |
| `apply` | Updates state to reflect new infrastructure |
| `destroy` | Removes destroyed resources from state |

## Exam Focus Areas (Associate 004)

- The order of the workflow: `init` → `plan` → `apply`
- What `terraform init` downloads and where it stores it (`.terraform/`)
- The purpose of `.terraform.lock.hcl`
- Plan symbols: `+`, `-`, `~`, `-/+`
- That `plan` makes no changes — it is read-only
- `-out` flag to save a plan and why it's used
- `-auto-approve` and when it's appropriate
- `terraform destroy` vs `terraform apply -destroy` (they are equivalent)
- `terraform validate` vs `terraform plan` — validate is offline, plan calls providers
- `terraform fmt` for consistent formatting
